## Exchange Formats and Lossy Conversion [#exchange-formats-and-lossy-conversion]

<Prose ids="cl-db30-exchange-formats-encode-worldviews cl-db30-simapro-and-eilcd-structural-limits cl-db30-olca-jsonld-and-tidas-open-schemas" />

Table 1. Comparison of six major LCA data-exchange formats across identification and linking, product-system support, lossy conversion limits, and specification status.

| Exchange Format | Identification & Linking | Product Systems & Parameters | Typical Lossy Conversion & Structural Limits | Specification Status |
| --- | --- | --- | --- | --- |
| EcoSpold 1 | Simple single-file process schema | No parameters or formulas | Severe loss when exporting modern parameterized or multi-output models | Legacy open format (largely retired) |
| EcoSpold 2 | Entity UUIDs + XML | Parameters, formulas, parent/child activities | Tightly coupled to ecoinvent structure; high adoption friction elsewhere | Public ecoinvent XML specification |
| ILCD / eILCD | Multi-type XML datasets + UUID refs | No global parameters; eILCD uses process instances | Awkward for matrix solvers; cannot distinguish same-flow same-location providers | Public European JRC specification |
| SimaPro CSV | Free-text name hard-linking | Multi-level parameters; no product-system entity | Name clashes in teams; cannot wire one process differently per system | Proprietary (no formal public spec) |
| openLCA JSON-LD | Typed `@id` refs + JSON-LD / RDF | Full product systems, formulas, multi-allocation, costs, EPDs | Lossless inside openLCA semantics; still degrades when exported to legacy formats | Public GreenDelta schema spec |
| TianGong TIDAS | Strongly typed open entities & validation | Open catalog semantics for flows, processes, and review metadata | Targets open validation & interoperability; proprietary software still needs adapters | Open-source specification (`tidas-spec`) |

## Software Implementation Differences and Reproducibility Audits [#software-implementation-differences-and-reproducibility-audits]

<Prose ids="cl-sw36-empirical-divergence-and-confounders cl-sw36-architecture-and-reproducibility-pinning" />

Table 2. Comparison of three major LCA software-implementation paradigms across data coupling, factor-pack and solver auditability, and typical cross-software reproducibility risks (synthesized from Iswara et al., 2020; Mutel, 2017; ILCD General Guide, 2010; openLCA schema and randonneur specifications).

| Software paradigm and example | Data-model and import/export coupling | Method-pack, linking, and solver auditability | Typical reproducibility risks and epistemic boundary |
| --- | --- | --- | --- |
| Bundled proprietary GUI suites (e.g., commercial SimaPro workflows) | Background libraries commonly bundled with commercial licenses; legacy exchange relies on name-linked CSV | Closed GUI execution limits line-by-line external inspection of internal factor matching and calculation steps | Cross-software export risks dropping non-transferable proprietary datasets; unpinned database and method versions can flip hotspots and top categories (cautionary evidence in Iswara et al., 2020) |
| Schema-typed open GUI ecosystems (e.g., openLCA) | Strongly typed JSON-LD schema with explicit flow-mapping tables (FlowMap), product systems, and provider strategies | Open source code allows auditing linking and unit-property conversions; LCIA method packs are free but excluded by default and must be installed to match | Missing or mismatched LCIA and normalization packs silently zero unmatched elementary flows (ILCD Section 8.2), collapsing categories such as eutrophication without errors |
| Modular scriptable open-source frameworks (e.g., Brightway) | Decouples data storage (Brightway2-data) from multi-source import/export (Brightway2-IO) and pairs cleanly with declarative randonneur migration recipes | Static and Monte Carlo matrix calculation (Brightway2-calc) and statistical array data format (stats_arrays) remain inspectable line by line in Python and Jupyter notebooks | Places full responsibility for pinning software environments, database releases, and migration scripts on the team; Mutel (2017) documents architecture only and reports no cross-software numerical benchmarks |
